QSP Stage393

PQC Readiness Evidence Execution Context, Input/Output Contract & External Review Handoff

This page explains how QSP is intended to be run, what the minimum reproducible inputs are, what machine-readable outputs it produces, which assumptions remain outside the cryptographic execution, and how the evidence model can sit downstream of CBOM or readiness-tracking data.

Scope boundary: QSP is a verification and evidence-binding layer. It is not a universal package inventory scanner, not a CBOM generator, not a PQC readiness tracker, and not a certification system.

1. Who runs it?

  • Developer/local: reproduce and inspect evidence.
  • CI: execute deterministic verification automatically.
  • Independent reviewer: rerun the same evidence and verifier without relying on the original developer's conclusion.

2. What are the inputs?

The minimal contract is intentionally narrower than a universal package or hardware taxonomy.

  • Immutable target identity: exact source commit, package/binary digest, firmware digest, container digest, or equivalent binding.
  • The specific PQC readiness claim and its scope.
  • Cryptographic algorithm or primitive and the behavior under test.
  • Immutable implementation identity.
  • Evidence identity: test vectors, signatures, keys, manifests, attestations, or other scoped evidence.
  • Execution profile and fail-closed policy.
  • Runtime/environment identity when it can materially affect interpretation.

Package name/version, PURL, CPE, bom-ref, CBOM asset reference, hardware model, firmware, build provenance, and readiness-tracker status can be carried as optional context unless the selected profile requires them. Unknown optional values are explicit; they are not guessed.

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

4. What are the outputs?

  • Target and claim identity.
  • Implementation and evidence bindings.
  • Environment record.
  • Execution counts, runtime errors, skips, and unsupported cases.
  • Expected-behavior and cross-implementation mismatch counts.
  • Decision and verification status.
  • Verified scope, assumptions, limitations, and explicit non-claims.
  • Hashable machine-readable JSON suitable for independent comparison.

5. Concrete Stage393 example

  • Wycheproof ML-DSA vector population: 1138
  • CIRCL executed: 1138
  • OpenSSL executed: 1138
  • Total cryptographic executions: 2276
  • CIRCL Wycheproof mismatches: 6
  • OpenSSL Wycheproof mismatches: 3
  • Cross-implementation mismatches: 9
  • Semantic behavior differences: 9
  • All 1138 vectors verified: false
  • Stage393 final acceptance: false

The nine observed differences are preserved as evidence. They are not automatically relabeled as a FIPS 204 nonconformance, implementation bug, or security vulnerability.

6. CBOM / readiness relationship

CBOM / package / hardware inventory
            ↓
readiness tracker claim or status
            ↓
QSP target + claim binding
            ↓
reproducible cryptographic evidence
            ↓
machine-readable result + assumptions + non-claims
            ↓
reviewer / tracker classification policy

QSP does not require a single universal CBOM schema. PURL, bom-ref, component references, cryptographic-asset references, build provenance, firmware identity, or tracker IDs can be carried as external context. The minimum fixed fields are the ones needed to reproduce and interpret the scoped evidence.

7. What feedback would be useful?

  • Is this minimal immutable evidence model technically meaningful for PQC readiness?
  • Which fields should be required across packages and hardware?
  • Which fields should remain optional or tracker-specific?
  • Which CBOM/PURL/component identifiers should be carried into target identity?
  • Which environment, provider, build, firmware, or hardware assumptions should be mandatory?
  • Is the separation between readiness classification and reproducible verification evidence appropriate?

Non-claims

This material does not claim PQCA endorsement, adoption, or acceptance. It does not claim formal certification, completed external assessment, complete FIPS 204 conformance, or system-wide quantum safety.

The previously closed Stage393 cryptographic authority is preserved unchanged. This context package performs no new cryptographic execution.
